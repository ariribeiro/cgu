03Engenharia de Software e Programação

Java é o centro. Esperar itens com trecho de código para você analisar.

Java: orientação a objetos, coleções e exceções

ALTA

Está literalmente no edital: tipos, controle, classes, encapsulamento, interfaces, herança, polimorfismo, coleções, generics, igualdade, mutabilidade, exceções e arquivos.

Fundamentos

  • Primitivos × wrappers: autoboxing; Integer pode ser null (NPE ao desempacotar).
  • String é imutável; use StringBuilder em loops.
  • Encapsulamento: atributos privados + acesso controlado.
  • Interface × classe abstrata: interface permite múltipla implementação e métodos default; abstrata guarda estado e construtor.
  • Sobrecarga (mesmo nome, outra assinatura, resolvida na compilação) × sobrescrita (subclasse, resolvida em execução = polimorfismo).
  • Herança simples de classe; super; construtores encadeados; final impede herança/sobrescrita.

Igualdade e mutabilidade

  • == compara referência (e valor em primitivos); equals() compara conteúdo.
  • Contrato: se a.equals(b) então a.hashCode()==b.hashCode(). Sobrescrever só um quebra HashMap/HashSet.
  • Objeto mutável como chave de HashMap: alterar o objeto depois de inserir “perde” a entrada.
  • Imutáveis: String, wrappers, record, List.of() (não aceita null e lança em add).
  • Cópia rasa × profunda.

Coleções e generics

  • List (ordem, duplicados: ArrayList acesso O(1), LinkedList inserção nas pontas) · Set (sem duplicados: HashSet, LinkedHashSet mantém inserção, TreeSet ordenado) · Map (HashMap O(1) médio, TreeMap O(log n) ordenado).
  • Generics: apagamento de tipo (type erasure), List<Object> não é supertipo de List<String>; curingas ? extends T (ler) e ? super T (escrever), a regra PECS.
  • Remover durante iteração: ConcurrentModificationException (use Iterator.remove() ou removeIf).

Exceções e arquivos

  • Checked (Exception, exige tratar/declarar, ex.: IOException) × unchecked (RuntimeException, Error).
  • finally sempre roda (exceto System.exit). try-with-resources fecha AutoCloseable sozinho.
  • catch mais específico antes do genérico, senão não compila.
  • Arquivos: Files.readAllLines, BufferedReader, Files.lines (stream, precisa fechar), Path/NIO.
try (var in = Files.newBufferedReader(Path.of("dados.csv"))) {
    String linha;
    while ((linha = in.readLine()) != null) { /* processa */ }
} catch (IOException e) {
    throw new UncheckedIOException(e);   // preserva a causa
}
Pegadinhas clássicas
  • “== em String compara conteúdo” → ERRADO (depende do string pool).
  • “Sobrescrever equals dispensa hashCode” → ERRADO.
  • “Todas as exceções precisam ser tratadas” → ERRADO (só as checked).
  • Polimorfismo: o método chamado depende do tipo real do objeto, não do tipo da variável (atributos e métodos estáticos não são polimórficos).

Concorrência e processamento

ALTA

Bloco inteiro dedicado no edital (3.1–3.4), com foco em condição de corrida, sincronização, bloqueios e falhas.

  • Concorrência (várias tarefas progredindo, intercaladas) × paralelismo (executando ao mesmo tempo em múltiplos núcleos) × assincronia (não bloquear esperando resultado: CompletableFuture, callbacks).
  • Condição de corrida: resultado depende da ordem de execução. Ex.: count++ não é atômico (ler-somar-gravar).
  • synchronized: exclusão mútua + visibilidade. volatile: garante visibilidade e ordem, mas não atomicidade.
  • AtomicInteger/CAS, ReentrantLock, ConcurrentHashMap (não bloqueia o mapa todo), CopyOnWriteArrayList.
  • Deadlock: locks em ordem diferente; prevenção = ordem global de aquisição, timeout (tryLock), escopo mínimo. Também livelock e starvation.
  • ExecutorService/pools: reaproveitam threads; pool pequeno limita paralelismo, bloqueio dentro de pool pode esgotá-lo.
  • Estado compartilhado mutável é a raiz do problema; mitigar com imutabilidade, confinamento a uma thread, ou estado externo (banco) com controle de concorrência.
  • Em requisições concorrentes (ex.: @Service singleton do Spring): não guardar estado mutável em atributo do bean.
// ERRADO: dois threads podem ler o mesmo valor
private int contador = 0;
void inc() { contador++; }

// CERTO
private final AtomicInteger contador = new AtomicInteger();
void inc() { contador.incrementAndGet(); }

Estruturas de dados, algoritmos, complexidade e padrões de projeto

MÉDIA

Cebraspe adora pedir “qual a complexidade” ou “o que esse pseudocódigo imprime”, além de teste de borda.

Complexidade

  • O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ).
  • Busca binária O(log n) exige ordenação. Ordenação por comparação: melhor possível O(n log n) (merge, heap; quick é O(n²) no pior caso).
  • HashMap O(1) médio, O(n) pior caso. Pilha (LIFO) × fila (FIFO) × deque.
  • Árvore balanceada O(log n); BFS usa fila, DFS usa pilha/recursão.
  • Loop dentro de loop sobre a mesma coleção: O(n²), e a decisão de desempenho costuma ser trocar por Map/Set.

Testes de borda

  • Lista vazia, um elemento, null, limites (off-by-one), números negativos, overflow de int, divisão por zero, datas/fuso.
  • Leia o código “como o compilador”: ordem de avaliação, i++ × ++i, curto-circuito &&/||.

Padrões de projeto (como apoio à manutenção)

  • Strategy (trocar algoritmo sem if/else) · Factory/Builder (criação) · Singleton (instância única; cuidado com estado global e testes) · Observer (eventos) · Decorator · Adapter (compatibilizar interfaces) · Facade · Template Method.
  • Princípios: SOLID, alta coesão e baixo acoplamento, preferir composição a herança, injetar dependências.

JavaScript e Vue.js

MÉDIA

Item 4.5 do edital: componentes, reatividade, eventos e consumo de APIs.

  • Componentes: reaproveitamento; props descem, eventos sobem (emit); não mutar prop no filho.
  • Reatividade (Vue 3): ref/reactive; computed (derivado, com cache) × watch (efeito colateral, ex.: chamar API).
  • Diretivas: v-if (monta/desmonta) × v-show (CSS); v-for com :key estável; v-model (two-way); @click, .prevent.
  • Ciclo de vida: onMounted é o lugar típico para a primeira chamada à API.
  • Consumo de APIs: fetch/axios são assíncronos (async/await, Promise); tratar loading, erro e vazio; fetch não rejeita em HTTP 4xx/5xx (conferir response.ok).
  • JS: === × ==, let/const/var, closures, event loop.
  • Segurança no front: v-html com conteúdo não confiável = XSS; token não deve ficar em localStorage se houver alternativa (cookie HttpOnly).

Requisitos, UX, acessibilidade e manutenção

BAIXA/MÉDIA

Itens conceituais, geralmente fáceis de acertar se você conhece os termos.

Requisitos

  • Funcionais (o que o sistema faz) × não funcionais (desempenho, segurança, usabilidade, disponibilidade, acessibilidade).
  • Critério de aceitação: verificável e objetivo (“dado… quando… então…”).
  • Restrições: legais, orçamentárias, tecnológicas, prazo.
  • Desenho centrado nas pessoas: pesquisa, personas, jornada, prototipação e teste com usuários reais.

UX e acessibilidade

  • Heurísticas de Nielsen: visibilidade do estado, prevenção de erros, consistência, reconhecer em vez de lembrar.
  • Prototipação: baixa × alta fidelidade; validação com usuários antes de codar é mais barato.
  • WCAG: perceptível, operável, compreensível, robusto (POUR). No Brasil: eMAG. HTML semântico, alt, contraste, navegação por teclado, leitores de tela (aria-*).
  • Responsivo: mobile first, media queries, unidades relativas.

Manutenção e evolução

  • Débito técnico: atalhos que cobram juros (bugs, lentidão); gerenciar com refatoração, testes e documentação.
  • Legados: sustentação × modernização; estratégia segura é incremental (Strangler Fig), com testes de caracterização antes de mexer.
  • Interoperabilidade: padrões abertos, contratos de API estáveis, compatibilidade retroativa.

Spring Framework e Spring Boot

ALTA

Itens 1.5–1.7: componentes, inversão de controle, injeção de dependências, configuração/autoconfiguração e serviços REST em camadas.

  • IoC: o contêiner cria e gerencia os objetos (beans), não o seu código. DI é a forma de entregar as dependências. Preferir injeção por construtor (imutável, testável, falha cedo).
  • Estereótipos: @Component, @Service, @Repository (tradução de exceções de persistência), @Controller/@RestController; @Configuration + @Bean.
  • Escopo padrão do bean = singleton (um por contêiner), logo, thread-safety importa.
  • @SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan.
  • Autoconfiguração: configura beans conforme o classpath e propriedades (condicionais); starters agrupam dependências; você sobrescreve definindo seu próprio bean.
  • Perfis (@Profile, application-prod.yml) e configuração externa (variáveis de ambiente) para separar ambientes. Segredos fora do código.
  • Camadas: Controller (HTTP) → Service (regra de negócio, @Transactional) → Repository (acesso a dados). Regra de negócio no controller = erro de design. Expor entidade JPA direto na API = acoplamento; use DTO.
  • REST no Spring: @GetMapping, @PathVariable, @RequestBody, @Valid (Bean Validation), @RestControllerAdvice para tratar erros de forma central.
@RestController
@RequestMapping("/api/v1/processos")
class ProcessoController {
    private final ProcessoService service;          // injeção por construtor
    ProcessoController(ProcessoService service) { this.service = service; }

    @PostMapping
    ResponseEntity<ProcessoDto> criar(@Valid @RequestBody NovoProcessoDto dto) {
        var criado = service.criar(dto);
        return ResponseEntity.created(URI.create("/api/v1/processos/" + criado.id())).body(criado);
    }
}

  • Status: 200 OK, 201 Created (+ Location), 204 No Content, 400 (requisição inválida), 401 não autenticado, 403 autenticado sem permissão, 404, 409 Conflict, 422, 429 (rate limit), 500, 503.
  • Recursos como substantivos (/processos/42), não verbos; coleções no plural; paginação, filtro e ordenação por query string.

  • Contrato: OpenAPI; testes de contrato evitam quebrar consumidores.
  • Repetição segura: cliente reenvia por timeout. Para POST, use chave de idempotência (Idempotency-Key) guardada pelo servidor.
  • Stateless: cada requisição carrega o necessário (facilita escala horizontal).

OAuth 2.0, OpenID Connect e tokens

ALTA

O edital destaca “OAuth 2.0 para autorização e OpenID Connect para autenticação federada”. A confusão entre os dois é pegadinha certa.

Quem faz o quê

  • OAuth 2.0 = autorização delegada: dar acesso limitado a um recurso sem compartilhar a senha. Não autentica por si só.
  • OIDC = camada de identidade/autenticação sobre o OAuth 2.0; adiciona o ID Token (JWT), o endpoint userinfo e o scope openid.
  • Papéis: Resource Owner, Client, Authorization Server, Resource Server.

Tokens

  • Access token: acessa a API (curta duração). Refresh token: renova o access token (guardar com mais cuidado). ID token: prova quem autenticou, é para o cliente, não para chamar API.
  • JWT = header.payload.signature; assinado, não criptografado (payload é legível, não ponha dado sensível).

Fluxos

  • Authorization Code + PKCE: padrão para SPA/mobile e web (PKCE protege contra interceptação do código).
  • Client Credentials: máquina a máquina, sem usuário.
  • Implicit e Password (ROPC): obsoletos/desaconselhados.

Validar token no Resource Server

  • Assinatura (chave pública/JWKS), iss (emissor), aud (destinatário), exp/nbf (validade), scopes/claims necessários.
  • Tokens curtos, TLS sempre, não registrar token em log, revogação/rotação do refresh token, state e nonce contra CSRF/replay.
Pegadinhas
  • “OAuth 2.0 é protocolo de autenticação” → ERRADO (é autorização; autenticação é OIDC).
  • “JWT é criptografado, então pode ter CPF” → ERRADO.
  • “Aceitar token só porque a assinatura é válida” → insuficiente: confira aud, iss e expiração.

Spring Security e controle de acesso

ALTA

Itens 2.5–2.8: segregação de funções, configuração, proteção de endpoints e métodos, e identificar/corrigir permissões excessivas (leitura de código esperada).

  • Autenticação (quem é) × autorização (o que pode). Fluxo: cadeia de filtros (SecurityFilterChain) → AuthenticationManager → SecurityContext.
  • Proteção por URL (requestMatchers(...).hasRole(...)) e por método (@EnableMethodSecurity, @PreAuthorize("hasRole('AUDITOR')")). Proteja ambos quando sensível, porque a URL sozinha falha se o método for chamado por outro caminho.
  • Ordem das regras importa: a primeira que casa vale; anyRequest().authenticated() por último. permitAll() amplo demais é a falha típica.
  • Negar por padrão (deny by default) e menor privilégio. Cuidado com hasRole("ADMIN") em tudo, curinga /** liberado, e papéis genéricos demais.
  • IDOR / BOLA (OWASP nº 1): autorizar só “é usuário logado” sem checar se o recurso é dele (GET /pedidos/123). Solução: checar posse/escopo no serviço (@PreAuthorize com expressão, ou filtro por usuário na query).
  • Senhas: hash adaptativo com salt (BCrypt/Argon2 via PasswordEncoder), nunca reversível, nunca MD5/SHA-1 puro.
  • CSRF: relevante com sessão/cookie; em API stateless com token no cabeçalho costuma ser desabilitado conscientemente. CORS não é mecanismo de autorização.
  • Segregação de funções: quem cria não aprova; papéis e permissões granulares, trilha de auditoria.
  • Resource Server: oauth2ResourceServer(jwt -> ...) valida o JWT por você.
http.authorizeHttpRequests(a -> a
    .requestMatchers("/publico/**").permitAll()
    .requestMatchers(HttpMethod.DELETE, "/api/**").hasRole("ADMIN")
    .anyRequest().authenticated())          // por último: negar por padrão
  .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));

Mensageria, consistência e integração

MÉDIA

Itens 3.1–3.4: mensageria, falhas, repetição, idempotência, consistência e evolução de contratos.

  • Fila (um consumidor processa cada mensagem) × tópico/pub-sub (vários assinantes). Kafka (log particionado, retenção), RabbitMQ (broker de filas).
  • Garantias: at-most-once (pode perder), at-least-once (pode duplicar; o mais comum), exactly-once (difícil; na prática = at-least-once + consumidor idempotente).
  • Consumidor idempotente: guardar ID da mensagem processada ou usar operação naturalmente idempotente. Dead-letter queue para mensagens venenosas; retry com backoff exponencial.
  • Sem transação distribuída (2PC é frágil): Saga (passos locais + compensação) e Outbox (grava evento na mesma transação do dado e publica depois, evita “gravou no banco mas não publicou”).
  • Consistência eventual; teorema CAP (sob partição, escolha entre consistência e disponibilidade).
  • Evolução de contrato: mudanças aditivas, campos opcionais, versionar schema, consumidores tolerantes; migração de esquema expandir → migrar → contrair (sem derrubar versão antiga).

Integração com dados e IA (LLM, RAG, agentes)

MÉDIA/ALTA

Tema novo e destacado no edital (4.1–4.5). Como é novidade, é terreno fértil para itens conceituais e de segurança.

  • Embeddings: vetores que representam significado; textos parecidos ficam próximos (similaridade do cosseno). Busca semântica ≠ busca por palavra-chave (esta é lexical, índice invertido).
  • RAG: recuperar trechos relevantes (banco vetorial) → colocar no prompt → gerar resposta fundamentada nas fontes. Reduz alucinação, atualiza o conhecimento sem retreinar, permite citar fontes.
  • Agentes e ferramentas: o modelo decide chamar funções/APIs (tool calling). Riscos aumentam com o poder das ferramentas.
  • Prompt injection (inclusive indireta): instruções maliciosas escondidas em documentos/páginas/e-mails que o modelo lê. Defesa: tratar conteúdo externo como dado, não instrução; menor privilégio para ferramentas; limitar escopo e permissões; confirmação humana em ações sensíveis; filtrar/validar saída; não dar ao modelo credenciais amplas.
  • Autorização na recuperação: filtrar o que o RAG busca pelas permissões do usuário (senão vaza documento que ele não poderia ver).
  • Avaliação funcional: conjunto de casos de teste, checar se a resposta está sustentada pela fonte, medir erros e vieses, não só “parece bom”. LLM é não determinístico.
  • Proteção de dados: não enviar dado pessoal/sigiloso a serviço externo sem base legal e salvaguardas; registrar/rastrear uso.

Confiabilidade: contêineres, nuvem, observabilidade e continuidade

MÉDIA/BAIXA

Item 5 do bloco de arquitetura.

  • Contêiner (Docker): processo isolado compartilhando o kernel do host, leve e portátil; imagem (modelo imutável) × contêiner (instância em execução). VM tem SO próprio.
  • Serverless/FaaS: sem gerenciar servidor, escala a zero, paga por uso; cold start, limites de tempo, difícil estado local.
  • IaaS × PaaS × SaaS. Kubernetes orquestra contêineres (réplicas, health checks, rolling update).
  • Observabilidade: logs (eventos), métricas (números no tempo), traces (caminho de uma requisição entre serviços; correlation ID).
  • Latência × vazão; disponibilidade (SLA/SLO); tolerância a falhas: timeout, retry com backoff + jitter, circuit breaker, bulkhead, fallback.
  • RTO (tempo para voltar) × RPO (quanto dado se aceita perder); backup testado; degradação graciosa.

05Persistência, Integração e Proteção de Dados

JPA, SQL, Spring Batch e privacidade: quatro áreas com muita chance de questão.

JPA e Spring Data JPA

ALTA

Itens 1.6–1.9: mapeamento, ciclo de vida, contexto de persistência, consultas, transações, carregamento (lazy/eager) e efeito sobre correção e desempenho.

Mapeamento

  • @Entity, @Id, @GeneratedValue, @Column, @Enumerated(EnumType.STRING) (ORDINAL quebra se reordenar o enum).
  • @ManyToOne, @OneToMany, @ManyToMany. O lado dono da relação é o que tem a FK; o outro usa mappedBy.
  • cascade propaga operações; orphanRemoval apaga filho removido da coleção.
  • Locking otimista com @Version (detecta conflito) × pessimista (bloqueia a linha).

Ciclo de vida e contexto

  • Estados: new/transient → managed → detached → removed.
  • Contexto de persistência (EntityManager): cache de 1º nível (mesma entidade = mesmo objeto na transação) e dirty checking: alterou uma entidade managed, o flush gera o UPDATE sozinho, sem chamar save().
  • persist (nova) × merge (devolve cópia managed).

Carregamento: o tema que mais cai

  • LAZY (carrega sob demanda; padrão em *ToMany) × EAGER (carrega junto; padrão em *ToOne).
  • LazyInitializationException: acessar associação LAZY com a sessão/transação já fechada. Soluções: join fetch, @EntityGraph, DTO/projeção, manter a transação aberta no serviço. (open-in-view “resolve” mas é má prática.)
  • Problema N+1: 1 consulta para a lista + N consultas para a associação de cada item → desempenho horrível. Corrigir com join fetch/@EntityGraph/batch size.
  • EAGER em tudo traz o grafo inteiro e piora o desempenho, e join fetch de coleção com paginação gera paginação em memória (HHH000104).

Transações (@Transactional)

  • Implementado por proxy: chamar método @Transactional de dentro da mesma classe (self-invocation) não abre transação. Método private/final também não funciona.
  • Rollback por padrão só em RuntimeException/Error; exceção checked não faz rollback, a menos que use rollbackFor.
  • Propagação: REQUIRED (padrão, junta-se à existente) × REQUIRES_NEW (nova, independente). readOnly=true é dica de otimização.
  • Colocar a transação no serviço (unidade de negócio), não no controller nem em cada repositório.

Spring Data JPA

  • JpaRepository<T,ID>: CRUD pronto; consultas derivadas do nome (findByStatusAndDataAfter); @Query (JPQL ou nativa); @Modifying em update/delete em lote.
  • Paginação: Pageable → Page (faz count extra) × Slice (sem count, mais barato). Sempre ordene para paginação ser determinística.
  • Projeções/DTO para trazer só as colunas necessárias.
@Query("select p from Processo p join fetch p.itens where p.orgao.id = :id")
List<Processo> buscarComItens(@Param("id") Long id);   // evita N+1

SQL e desempenho

ALTA

Cebraspe cobra SQL com consulta escrita no item. Treine ler a query e prever o resultado.

Consultas

  • JOIN: INNER (só casados), LEFT (todos da esquerda, NULL onde não casa), FULL, CROSS (produto cartesiano).
  • WHERE filtra linhas antes de agrupar; HAVING filtra grupos depois (usa agregados).
  • Subconsultas: IN, EXISTS (costuma ser melhor com muitos dados), correlacionadas.
  • CTE (WITH ... AS): organiza queries; recursiva para hierarquias.
  • Funções de janela: ROW_NUMBER(), RANK(), SUM() OVER (PARTITION BY ...) (não colapsam linhas, ao contrário do GROUP BY).

Controle e dados

  • DDL (CREATE/ALTER/DROP) · DML (INSERT/UPDATE/DELETE/SELECT) · DCL (GRANT/REVOKE) · TCL (COMMIT/ROLLBACK).
  • Menor privilégio em GRANT; evitar conta da aplicação como dona do esquema.
  • ACID; níveis de isolamento: dirty read, non-repeatable read, phantom; deadlock no banco.

NULL e duplicações (pegadinhas do tema)

  • NULL = desconhecido; = NULL nunca é verdadeiro, use IS NULL. Lógica de três valores.
  • COUNT(*) conta linhas; COUNT(coluna) ignora NULL; SUM/AVG ignoram NULL.
  • NOT IN com NULL na lista retorna vazio, por isso prefira NOT EXISTS.
  • Colunas NULL em JOIN não casam entre si; UNION remove duplicatas × UNION ALL não (e é mais rápido). JOIN em chave não única multiplica linhas (duplicação).

Índices e planos de execução

  • Índice B-tree acelera leitura (filtro, junção, ordenação) mas custa escrita e espaço.
  • Índice composto: vale a regra do prefixo mais à esquerda.
  • Função na coluna desativa o índice (WHERE YEAR(data)=2026, LIKE '%abc'): condições “não sargáveis”. Use faixa: data >= '2026-01-01' AND data < '2027-01-01'.
  • Baixa seletividade (ex.: flag S/N) = índice pouco útil. Covering index evita ir à tabela.
  • EXPLAIN: seq scan × index scan; estatísticas desatualizadas levam a planos ruins; SELECT * e consultas em loop (N+1) são vilões da aplicação.
-- Quem NÃO tem pagamento? (seguro com NULL)
SELECT c.id FROM contrato c
WHERE NOT EXISTS (SELECT 1 FROM pagamento p WHERE p.contrato_id = c.id);

WITH ranking AS (
  SELECT orgao, valor, ROW_NUMBER() OVER (PARTITION BY orgao ORDER BY valor DESC) rn
  FROM despesa)
SELECT * FROM ranking WHERE rn = 1;   -- maior despesa por órgão

Spring Batch

ALTA

Seis subitens só dele (3.6–3.9). É raro um edital detalhar tanto uma biblioteca; espere perguntas conceituais sobre reinício e reprocessamento.

Estrutura

  • Job contém um ou mais Steps.
  • Step de chunk: ItemReader → ItemProcessor → ItemWriter. Lê item a item, processa, acumula e grava em bloco (chunk size = intervalo de commit: 1 transação por chunk).
  • Step Tasklet: uma tarefa simples (limpar diretório, etc.).
  • Processador devolvendo null filtra o item (não vai ao writer).

Estado e reinício

  • JobRepository persiste metadados: JobInstance (job + JobParameters de identificação), JobExecution (cada tentativa), StepExecution.
  • Mesmos parâmetros de um job FAILED = reinício do ponto da falha; de um job COMPLETED = erro (instância já concluída), a menos que mude parâmetro.
  • Reader com estado (guarda posição no ExecutionContext) permite retomar; reader sem estado reprocessa do início.
  • Tolerância a falhas: skip (ignora e segue, com limite), retry (tenta de novo para falhas transitórias), listeners.
  • Evitar perda e duplicação: commit por chunk + estado persistido; writer idempotente (upsert/chave única), pois o chunk que falhou é desfeito mas efeitos externos (ex.: e-mail, API) não.
  • Ler de arquivo/banco com paginação ou cursor para não estourar memória; processar incremental por marca d’água.

Privacidade e segurança de dados (LGPD)

ALTA

Item 4 do bloco, repetido em transparência (complementares). Pergunta típica: “qual técnica/princípio se aplica aqui?”.

  • Princípios (Lei 13.709/2018, art. 6º): finalidade, adequação, necessidade (minimização), livre acesso, qualidade, transparência, segurança, prevenção, não discriminação, responsabilização.
  • Dado pessoal (identifica ou pode identificar) × sensível (saúde, origem racial, religião, opinião política, biometria, vida sexual etc.) × anonimizado (não identifica; fora da LGPD se irreversível).
  • Pseudonimização ≠ anonimização: troca identificadores por códigos, mas com a chave dá para reidentificar, então continua sendo dado pessoal. Risco de reidentificação por cruzamento de bases (quase-identificadores: CEP + nascimento + sexo).
  • Criptografia: em trânsito (TLS) e em repouso (AES, disco/campo/banco); gestão de chaves separada dos dados; hash não é criptografia (é irreversível; para senha, usar hash lento com salt).
  • Minimização, finalidade, acesso e segregação: coletar só o necessário, usar para o fim declarado, acesso por necessidade (need to know), separar dados identificáveis dos demais.
  • Retenção e descarte: prazo definido, eliminação segura, e cópias (backups, logs, ambientes de teste, planilhas) também entram.
  • Compartilhamento/publicação: base legal, tarjamento, agregação, dados abertos sem dados pessoais; compatibilizar com a Lei de Acesso à Informação.
  • Privacy by design/default (desde a concepção): privacidade como requisito da arquitetura, configuração mais protetiva por padrão, RIPD (relatório de impacto).
  • Não logar dado pessoal/sensível; não usar produção real em testes sem mascaramento.

Fluxos de dados, ETL/ELT e formatos

MÉDIA

Itens 3.1–3.5: ingestão, transformação, lote × fluxo, completo × incremental, formatos e repetição segura.

  • ETL: transforma antes de carregar (em área de staging). ELT: carrega bruto e transforma dentro do destino (comum em data lake/warehouse na nuvem).
  • Lote (batch: janelas, alto volume, latência maior) × fluxo (stream: evento a evento, baixa latência).
  • Carga completa (recarrega tudo; simples e cara) × incremental (só o novo/alterado: marca d’água por data/ID, ou CDC; atenção a exclusões e atrasos).
  • Formatos: CSV (simples, sem tipos/esquema, problemas com delimitador e codificação) · JSON (aninhado, legível, verboso) · XML (esquema XSD, namespaces, verboso) · Parquet (colunar, comprimido, tipado, ótimo para análise; leitura seletiva de colunas).
  • Qualidade e rastreabilidade: validar esquema, nulos, duplicidades; linhagem (de onde veio); conciliação (contagem/soma origem × destino).
  • Reprocessamento seguro: operações idempotentes (upsert, chave natural), carga em tabela temporária + swap, registro do que já foi processado.

Modelagem, NoSQL, cache e busca

MÉDIA/BAIXA

Item 1 do bloco. Conceitos básicos resolvem a maioria.

  • Normalização: 1FN (valores atômicos) → 2FN (sem dependência parcial da chave) → 3FN (sem dependência transitiva). Reduz redundância e anomalias; desnormalizar conscientemente para leitura/desempenho.
  • Integridade: PK, FK (referencial), UNIQUE, NOT NULL, CHECK.
  • Escolha do armazenamento conforme o uso: relacional (transações, integridade, consultas ad hoc) · documental (MongoDB: dados aninhados, esquema flexível) · chave-valor (Redis: acesso por chave, cache, sessão) · vetorial (busca por similaridade de embeddings).
  • Cache: cache-aside, TTL, invalidação (o difícil), risco de dado desatualizado; cache nunca é fonte da verdade.
  • Busca textual (Elasticsearch/OpenSearch): índice invertido, relevância, stemming; complementa o banco, não o substitui.
  • Evolução de esquemas: migrations versionadas (Flyway/Liquibase), mudanças compatíveis em duas fases.

06Desenvolvimento Seguro, Qualidade e Gestão da Entrega

Segurança de aplicação e testes são rentáveis. Contratação e gestão rendem itens conceituais “fáceis”.

Segurança de aplicações (OWASP)

ALTA

Ameaças, validação de entrada, controle de acesso, segredos, dependências, testes autorizados, vazamentos e tratamento de falhas (inclusive com IA).

OWASP Top 10 (essencial)

  • Broken Access Control (IDOR, falta de checagem no servidor).
  • Cryptographic Failures (dados sem TLS, algoritmo fraco).
  • Injection (SQL, comando, LDAP) e XSS.
  • Insecure Design · Security Misconfiguration (padrões, mensagens de erro verbosas, S3 aberto).
  • Vulnerable/Outdated Components · Auth Failures · Integrity Failures (cadeia de suprimentos).
  • Logging/Monitoring Failures · SSRF.

Defesas

  • SQL injection: consultas parametrizadas (PreparedStatement, JPA :param), nunca concatenar. Validar entrada é complemento, não substituto.
  • XSS: codificar a saída conforme o contexto, CSP, evitar innerHTML/v-html.
  • CSRF: token anti-CSRF, SameSite.
  • Validar no servidor (a validação do front é só UX); allowlist > denylist; limitar tamanho, tipo (upload!).
  • Segredos: nunca no repositório/imagem/log; usar vault/variáveis de ambiente; rotação; secret scanning. Segredo commitado = considerar comprometido (revogar, não só apagar).
  • Dependências: SCA, SBOM, atualização, fixar versões, atenção a pacotes maliciosos (typosquatting).
  • Testes de segurança autorizados: SAST (código), DAST (aplicação rodando), SCA, pentest com autorização escrita e escopo.
  • Prevenção de vazamentos: mensagens de erro genéricas ao usuário (detalhes só no log), sem stack trace exposto, minimizar dados em respostas de API.
  • Tratamento de incidentes: registros (logs) íntegros e sem dado sensível, preservar evidências (cadeia de custódia, não alterar), conter → erradicar → recuperar, comunicar.
  • Com IA: injeção de prompt, vazamento via contexto/saída, logs que guardam prompts com dados pessoais, ferramentas com permissão excessiva.

Entrega e operação: CI/CD e DevSecOps

ALTA

Item 3 do bloco.

  • Integração contínua (CI): integrar com frequência no tronco, com build + testes automáticos a cada commit. Entrega contínua: sempre pronto para produção, com aprovação manual para implantar. Implantação contínua: vai para produção automaticamente.
  • DevSecOps: segurança em todo o ciclo (shift left): SAST, SCA, secret scanning, DAST, varredura de imagens na pipeline.
  • Cadeia de suprimentos: dependências verificadas, versões fixadas (lock files), artefatos assinados, build reprodutível, repositório interno de artefatos, SBOM.
  • Automação de build/teste/implantação: pipeline como código; o mesmo artefato promovido entre ambientes (build once, deploy many); IaC.
  • Ambientes segregados (dev/homologação/produção): configuração externa, dados e credenciais distintos, sem dado real em dev.
  • Mudanças e reversão: rolling, blue-green (dois ambientes, troca de tráfego), canary (pequena parcela primeiro), feature flags; plano de rollback; migrações de banco compatíveis com a versão anterior.
  • Observabilidade para detectar regressão após o deploy; continuidade durante entregas e incidentes: janela, comunicação, post-mortem sem culpados.
  • Versionamento: Git, trunk-based × GitFlow, versionamento semântico (MAJOR.MINOR.PATCH).

Gestão de produtos digitais, Scrum, Kanban e governança

MÉDIA

Item 4. Conceitos de gestão com o “sabor CGU”: PDTIC, transformação digital e dados abertos.

Scrum

  • Papéis: Product Owner (maximiza valor, dono do Product Backlog e prioridade), Scrum Master (remove impedimentos, garante o processo), Developers (autogerenciados; decidem como).
  • Eventos: Sprint (≤ 1 mês), Planejamento, Daily (15 min), Revisão, Retrospectiva.
  • Artefatos e compromissos: Product Backlog → Meta do Produto; Sprint Backlog → Meta da Sprint; Incremento → Definição de Pronto (DoD).
  • Critérios de aceitação (por item) × DoD (comum a todos).

Kanban e produto

  • Kanban: visualizar fluxo, limitar WIP, gerenciar fluxo (lead time, cycle time, vazão); fluxo contínuo, sem sprint obrigatória.
  • Descoberta de necessidades (entender o problema antes de construir), MVP, hipóteses, ciclo de vida do produto (descoberta → entrega → evolução → descontinuação).
  • Priorização: valor × esforço, MoSCoW, WSJF. Indicadores de resultado (outcome: o problema melhorou?) × produto de entrega (output: entregamos a funcionalidade?).
  • PDTIC (Plano Diretor de TIC): planejamento de TI do órgão, alinhado à estratégia institucional; base para priorização e contratações. Plano de Transformação Digital (serviços digitais, Gov.br) e Plano de Dados Abertos (PDA): publicar dados reutilizáveis em formato aberto e legível por máquina, respeitando a proteção de dados pessoais. Esses planos devem aparecer como requisitos de produtos e integrações.
  • Riscos, responsabilidades e evidências de efetividade: risco → controle → evidência de que o controle funciona (conversa direta com a auditoria).

Contratação e fiscalização de soluções de TI

MÉDIA

Item 5: ETP, TR, comparação “fazer × comprar × compartilhar”, custo total, SLA, fiscalização, propriedade intelectual e plano de saída. Como a prova é de auditor, a ótica é de controle.

  • Sequência: necessidade → ETP (Estudo Técnico Preliminar) (justifica a necessidade, compara alternativas, estima custo, avalia viabilidade) → Termo de Referência (especifica o objeto, requisitos, critérios de aceite, SLA, obrigações) → licitação → contrato → fiscalização → pagamento.
  • Alternativas: desenvolvimento próprio × contratação (fábrica de software, serviço) × compartilhamento (reuso de solução de outro órgão, software público). Considerar capacidade da equipe, custo de manutenção, risco, prazo, dependência.
  • Custo Total de Propriedade (TCO): aquisição + implantação + operação + manutenção + treinamento + saída, e não só o preço da licença.
  • Pesquisa de preços: múltiplas fontes (contratos similares, painel de preços, fornecedores), evitando preço de uma fonte só e cuidado com sobrepreço.
  • Níveis de serviço (SLA/ANS) mensuráveis, com glosa proporcional ao descumprimento; critérios de aceitação objetivos; pagamento vinculado a entregas verificadas (por resultado), não por horas ociosas.
  • Fiscalização: separar gestor, fiscais técnico/administrativo/requisitante; atestar só o que foi verificado; pagamento só após aceite.
  • Propriedade intelectual: no desenvolvimento contratado, prever cessão dos direitos, entrega do código-fonte e documentação (Lei 9.609/1998 – software); portabilidade de dados, acesso aos dados e formatos abertos, evitar lock-in, e plano de saída/transição (transferência de conhecimento).
  • Base normativa para revisar: Lei 14.133/2021 e normas de contratação de soluções de TIC do governo federal (SGD).

P2 — Complementares (mín. 12 de 40)

08Prova discursiva

Vale tanto quanto toda a parte objetiva na nota final. Só é corrigida para os mais bem colocados nas objetivas.

  • Questão 1 (30 pts · até 30 linhas): conhecimentos complementares (governança, integridade, transparência, auditoria).
  • Questão 2 (70 pts · até 60 linhas): situação-problema de TI. Esperam diagnóstico, decisão e justificativa técnica.
  • Texto dissertativo, coerente e coeso, em norma culta. Nota = conteúdo − penalidade por erros (NQ1 = NC − 6×NE ÷ TL). Cada erro de português desconta; escreva o texto inteiro, mas sem ultrapassar o limite (o excedente é desconsiderado).
  • Aprovação na discursiva: NFPD ≥ 50 de 100. Manuscrito, caneta preta, sem identificação.

Roteiro para a situação-problema (60 linhas)

  1. Contextualize o problema e o risco (1–2 frases).
  2. Diagnostique: causas prováveis e o que verificar (logs, métricas, queries, permissões).
  3. Proponha a solução técnica, com a tecnologia certa (ex.: join fetch contra N+1; Outbox + consumidor idempotente; PKCE; parametrização; chunk + restart no Batch).
  4. Compare alternativas e trade-offs (custo, risco, prazo, segurança, desempenho).
  5. Controles e evidências: testes, observabilidade, rollback, LGPD, segregação de funções.
  6. Conclua com a recomendação priorizada.

Cenários prováveis para treinar

  • API com falha de controle de acesso (IDOR, permissões excessivas) e como corrigir/testar.
  • Lentidão por N+1, índice ausente ou consulta não sargável.
  • Job batch que duplica ou perde registros após falha e reinício.
  • Integração por mensageria com duplicidade e consistência (Outbox/Saga/idempotência).
  • Uso de IA/RAG com vazamento de dados ou prompt injection.
  • Escolha entre monolito × microsserviços, ou desenvolver × contratar × compartilhar, com ótica de risco e custo.
  • Vazamento de dado pessoal: minimização, pseudonimização, retenção, resposta a incidente.
